## Ключевые бизнес-сценарии (проверочные точки целевой архитектуры)

| ID  | Сценарий                                      | Ожидаемый результат через год                                                                                                   |
| --- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| S1  | Самообслуживание доменных аналитиков          | Сотрудник строит отчёт по своим срезам за минуты без заявки в ИТ                                                                |
| S2  | Кросс-доменная управленческая отчётность      | Консолидированные KPI головного офиса за часы вместо дней, из единых бизнес-метрик                                              |
| S3  | Операционная работа клиник                    | Врачи/операторы работают с ЭМК; медицинские карты, истории болезни и результаты исследований **не включаются** в витрину данных |
| S4  | Независимое развитие финтех- и ИИ-направлений | Домены развивают свои данные и сервисы без согласования транзитных изменений через общий DWH                                    |
| S5  | Безопасность и соответствие регуляторам       | Разграничение доступа на уровне домена/среза, маскирование ПДн, аудит, банковская и медицинская тайна                           |
| S6  | Масштабирование на новые бизнесы              | Новый домен (фарма, электроника) получает типовую data-платформу и доступ к витрине за дни, без доработок центрального DWH      |
| S7  | Отказоустойчивость и непрерывность            | Геораспределённое развёртывание, РБ/DR, SLA на отчётность                                                                       |

## Реестр проблемных мест

| ID  | Проблема                                                                                           | Причина (в текущем ландшафте)                                                                                                               | Пострадавшие бизнес-сценарии | Бизнес-эффект                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| P1  | Медленное построение отчётности: сложные отчёты формируются **часами**                             | Сотни ТБ данных в едином DWH на SQL Server 2008; огромное количество трансформаций; конкуренция нагрузок операционки и аналитики в одной БД | S1, S2, S7                   | Задержки в принятии управленческих решений; менеджеры получают данные «вчерашним днём»; падение производительности аналитических процессов |
| P2  | Значительная часть **бизнес-логики доменов зашита в DWH** (финансовая логика, логика ИИ-обработки) | Исторически DWH был единой точкой интеграции и трансформации                                                                                | S4, S6                       | Развитие финтеха и ИИ требует изменения общего DWH → согласования, очереди релизов, рост time-to-market; высокая цена ошибки в общем ядре  |
| P3  | **Монолитность DWH**: любые новые бизнесы (фарма, электроника) наследуют тот же контур             | Нет доменных границ, нет соглашений о данных                                                                                                | S4, S6                       | Подключение нового направления = месяцы доработок и миграций; масштабирование ограничено вертикальной ёмкостью SQL Server                  |
| P4  | **BI-кастомизации поверх DWH** (Power BI + большие слои кастомизации)                              | Логика отчётов дублируется и разрастается в BI-слое; нет единого каталога и семантики метрик                                                | S1, S2                       | Одна и та же метрика считается по-разному в разных отчётах; недоверие к цифрам; рост стоимости поддержки BI                                |
| P5  | **Устаревший и уязвимый стек**: SQL Server 2008 (вне поддержки Microsoft), PowerBuilder            | Легаси-платформы без патчей безопасности                                                                                                    | S5, S7                       | Риски комплаенса для мед. и фин. данных (требования регуляторов, банковская лицензия); риск простоев без вендорской поддержки              |
| P6  | **Единая точка отказа** — DWH и старая шина (ESB Apache Camel)                                     | Централизованная интеграция без геораспределения                                                                                            | S2, S7                       | Отказ DWH/ESB парализует и операционку, и отчётность; нет DR-плана, соответствующего требованиям к банку и клиникам                        |
| P7  | **Интерфейс PowerBuilder** связывает клиники с DWH напрямую                                        | Клиент оператора зависит от устаревшего ядра                                                                                                | S3, S5                       | Невозможно модернизировать UX клиник без переписывания; риски ПДн в толстом клиенте                                                        |
| P8  | **Нет разграничения доступа по доменам и срезам** в текущей модели                                 | Единая БД, права на уровне таблиц                                                                                                           | S1, S5                       | Пользователь одного домена теоретически видит данные другого; регуляторные риски (мед. тайна, банковская тайна, 152-ФЗ)                    |
| P9  | **Долгий time-to-market изменений**: каждая новая витрина/отчёт — заявка в DWH-команду             | Централизованная команда, очередь трансформаций                                                                                             | S1, S4, S6                   | Аналитики простаивают, бизнес теряет скорость реакции на рынок                                                                             |
| P10 | **Медицинские чувствительные данные и аналитические нагрузки смешаны**                             | DWH содержит ЭМК и одновременно обслуживает отчётность                                                                                      | S3, S5                       | Санкции за утечки, избыточный доступ к мед. данным; невозможность корректно выделить обезличенные срезы для аналитики                      |

## Как целевая архитектура закрывает проблемы (сводка)

| Проблема | Решение в целевой архитектуре (через год)                                                                                                                                                                                                       |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1       | Data-продукты на Lakehouse в каждом домене + интерактивный Query Engine: отчёт за минуты (S1, S2)                                                                                                                                               |
| P2       | Бизнес-логика возвращается в домены (финтех-сервисы, ИИ-сервисы, data-продукты); DWH замораживается и мигрирует (S4)                                                                                                                            |
| P3       | Data Mesh: новый домен разворачивает типовую платформу из шаблона (S6)                                                                                                                                                                          |
| P4       | Data Catalog + Semantic Layer: единые сертифицированные метрики; BI-кастомизации мигрируют в Report Builder (S1, S2)                                                                                                                            |
| P5       | Миграция в облако, SQL Server 2008 и PowerBuilder выводятся из эксплуатации (S5, S7)                                                                                                                                                            |
| P6       | Kafka (event backbone) + геораспределённое развёртывание, RB/DR per домен (S7); поэтапный вывод ESB: переезд преобразований (потоковых и batch), ФЛК, бизнес-логики и паттернов надёжности — [`esb-decommissioning.md`](esb-decommissioning.md) |
| P7       | Клиники переходят на современный интерфейс МИС/ЭМК; PowerBuilder выводится (S3)                                                                                                                                                                 |
| P8       | IAM (RBAC/ABAC) + Data Governance: доступ на уровне среза, маскирование, аудит (S1, S5)                                                                                                                                                         |
| P9       | Self-service портал: аналитик сам строит отчёты и витрины (S1, S4, S6)                                                                                                                                                                          |
| P10      | ЭМК остаётся в медицинском домене; в витрину данных попадают только обезличенные операционные срезы (S3, S5)                                                                                                                                    |
