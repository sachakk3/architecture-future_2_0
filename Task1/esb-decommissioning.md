# Вывод ESB (Apache Camel): переезд интеграционной функциональности

**Связанные документы:**

- Реестр проблем: [`problems.md`](problems.md) (P6 — единая точка отказа ESB/DWH)
- Целевая архитектура: [`c4-container-diagram.puml`](c4-container-diagram.puml)
- Приоритизация: [`prioritization.md`](prioritization.md)

## 1. Почему «замены на Kafka + API Gateway» недостаточно

ESB (Apache Camel) сегодня — это не просто «труба» между системами. За годы эксплуатации
в маршрутах Camel накопилась интеграционная функциональность четырёх классов:

| Класс функциональности ESB             | Примеры в текущем ландшафте                                                                                                         |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Транспорт и маршрутизация**          | Связывание МИС/ЭМК, банковского ядра, финтех-сервисов, корпоративных систем и DWH по ~100+ интеграциям (HTTP, JMS, FTP, SOAP, JDBC) |
| **Преобразования** (streaming и batch) | Форматные трансформации (XML↔JSON↔CSV↔ фикс. форматы), обогащение, агрегация, каналы загрузки в DWH                                 |
| **ФЛК** (форматно-логический контроль) | Проверка схем и структур входящих сообщений/файлов, бизнес-правил, справочников; отбраковка и возврат ошибок                        |
| **Бизнес-логика интеграций**           | Оркестрация процессов (списание из банка → уведомление в МИС), сведение данных, сквозные бизнес-правила                             |
| **Паттерны надёжности**                | Retry, DLQ, circuit breaker, идемпотентность, транзакционные гарантии доставки, backpressure                                        |

Если просто «подключить Kafka», все эти функции останутся без владельца: трансформации и ФЛК
не исчезнут — они переедут или в **домены**, или на **платформу данных**. Ниже — целевое
распределение и план миграции каждого класса.

## 2. Принцип миграции: «smart endpoints, dumb pipes»

ESB не переносится как единое целое. Целевое распределение его функций:

- **Kafka** — только транспорт событий и буферизация (event backbone), без бизнес-логики;
- **API Gateway** — только синхронный внешний контур (REST/gRPC для внешних партнёров,
  мобильных клиентов и клиник), вместе с IAM;
- **Домены (финтех, медицина, корпоративный)** — бизнес-логика и оркестрации возвращаются
  в доменные сервисы (Golang/Java), как и логика из DWH (см. P2);
- **Платформа данных** — преобразования и ФЛК данных (data contracts, Schema Registry,
  batch-валидация) становятся частью контрактов data-продуктов.

## 3. Миграция преобразований

### 3.1 Потоковые (event-driven) интеграции

| Было в Camel                                                    | Станет в целевой архитектуре                                                                                                           |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Camel-маршруты «получил сообщение → трансформировал → отправил» | Producer пишет событие в **нормализованном формате** (Avro/Protobuf, JSON-схема в Schema Registry); трансформация на стороне источника |
| Трансформации «на лету» внутри маршрутов                        | **Kafka Streams / Flink** в доменных data-платформах (Streaming Platform) — обогащение, windowing, агрегация                           |
| Каналы «система → ESB → DWH» (операционные события в DWH)       | **CDC (Debezium)** напрямую из БД источников → Kafka → инжест в Lakehouse домена; ESB из цепочки исключается                           |
| Форматные конвертации под каждого потребителя                   | Одна каноническая схема события (data contract) на продюсере; потребители читают свой view через доменные data-продукты                |

Потоковые трансформации, которые обслуживают **операционные** сценарии (не аналитические),
переносятся внутрь доменных сервисов — например, финтех-сервис сам публикует
«ПлатёжПроведён» в каноничной схеме, вместо того чтобы Camel конвертировал XML банковского
ядра под каждого подписчика.

### 3.2 Пакетные интеграции (файлы, массовые выгрузки)

| Было в Camel                                     | Станет в целевой архитектуре                                                                                                          |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| FTP/файловые каналы через ESB в DWH              | **Batch-коннекторы платформы данных** (Kafka Connect / Spark batch / Airflow-джобы) → S3 Lakehouse домена                             |
| Периодические выгрузки DWH → системы-потребители | Data-продукты доменов + экспорт из Lakehouse (парт-файлы в S3) или подписка на CDC-поток; витрина данных как источник отчётных срезов |
| Сложные batch-трансформации (сведение, расчёты)  | Spark/Delta-пайплайны в доменных платформах — под контролем доменной команды, без очереди в центральную интеграционную                |

### 3.3 API-интеграции (синхронные)

- REST/SOAP-проксирование Camel → **API Gateway** (маршрутизация, лимиты, IAM/SSO, версионирование);
  SOAP-эндпойты легаси-систем остаются за антикоррупционным фасадом до их вывода.
- Тяжёлые синхронные цепочки переводятся на **async**: «запрос → событие в Kafka → ответ по
  callback/webhook», чтобы исключить блокирующие зависимости через шину.

## 4. Миграция ФЛК (форматно-логического контроля)

ФЛК в Camel выполнялся на границе «всех со всеми». В целевой модели контроль переезжает
на контрактную модель и распределяется по уровням:

| Уровень ФЛК                                         | Где выполняется в целевой архитектуре                                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Схемный контроль** (структура, форматы полей)     | На **продюсере** при публикации в Kafka: Avro/JSON-схема проверяется Schema Registry (compatibility-политики); в API Gateway — JSON Schema/OAS-валидация запросов |
| **Логический контроль** (бизнес-правила)            | **Data Contracts** доменных data-продуктов + валидаторы (Great Expectations / Deequ / Kafka Streams-валидаторы) в доменных платформах                             |
| **Справочная целостность** (реквизиты, справочники) | В **Semantic Layer** и доменных сервисах: нормализация справочников (ID клиник, счетов) при инжесте в Lakehouse                                                   |
| **Контроль batch-файлов**                           | Валидационные гейты в Airflow-пайплайнах: schema check → business rules → quarantine                                                                              |

**Обработка ошибок вместо Camel-отбраковки:**

- сообщения, не прошедшие ФЛК, не «молча» отбрасываются, а попадают в
  **quarantine/DLQ-топики** с метаданными причины — сервисы домена обрабатывают и переотправляют;
- для batch — **quarantine-зоны в S3** + задачи переобработки в Airflow;
- статистика ФЛК (доля брака по контрагенту/каналу) — метрика качества данных
  в Data Catalog и Observability.

Правила ФЛК, зашитые в маршрутах Camel, выгружаются в репозиторий контрактов данных
(как код) при инвентаризации — иначе они будут потеряны вместе с шиной.

## 5. Миграция бизнес-логики из ESB

| Тип логики в Camel                                                         | Куда переезжает                                                                                                              |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Оркестрации процессов** («шаг 1 → шаг 2 → шаг 3» через несколько систем) | Доменные сервисы (Golang/Java) на паттернах **Saga / Process Manager**; событие-команда через Kafka вместо вызова через шину |
| **Агрегации и сведение** (собрать ответ из 3 систем)                       | Либо в доменный сервис (для операционных сценариев), либо в data-продукт/Lakehouse (для аналитических)                       |
| **Сквозные бизнес-правила** (пересчёты, флаги)                             | В домены — вместе с бизнес-логикой из DWH (см. P2); в ESB-замене остаётся только маршрутизация                               |
| **Роутинг и условия по содержимому** (content-based routing)               | Подписки доменов на топики Kafka + фильтрация на стороне потребителя; сложные условия — в Kafka Streams                      |

Ключевой принцип: **логика не может «переехать в Kafka»** — она обязана получить владельца
в домене. При инвентаризации каждый маршрут Camel классифицируется: транспорт / трансформация /
ФЛК / бизнес-логика — и по классу определяется целевой владелец (см. таблицу в §2 и §7).

## 6. Миграция паттернов надёжности

В Camel надёжность обеспечивалась возможностями шины. В событийной архитектуре гарантии
достигаются иначе:

| Паттерн в ESB (Camel)                               | Целевой аналог на Kafka + доменах                                                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Retry** (повторные попытки доставки)              | Ретраи на уровне продюсера (acks=all, retries) + ретраи с backoff в consumer-сервисах; ретраи вне процесса — retry-топики с задержкой (retry topics)                          |
| **Dead Letter Queue**                               | **DLQ-топики Kafka** (dead-letter queue per consumer group) + переобработка через инструмент домена; ошибки видимы в Observability                                            |
| **Гарантия доставки** (transactions Camel)          | **At-least-once** по умолчанию; для критичных финтех-потоков — **exactly-once** (транзакции Kafka) или идемпотентный consumer                                                 |
| **Идемпотентность** (idempotent consumer)           | **Идемпотентный producer** + дедупликация по ключу события (event ID) на consumer-стороне; для БД — upsert по естественному ключу                                             |
| **Transactional inbox/outbox**                      | **Transactional Outbox + Debezium**: изменения БД публикуются в Kafka гарантированно вместе с транзакцией источника; inbox — для строгой обработки входящих событий в доменах |
| **Circuit Breaker**                                 | Resilience4j/перемычки в доменных сервисах (для исходящих HTTP/gRPC); асинхронность Kafka снимает каскадные отказы «через шину»                                               |
| **Backpressure / throttling**                       | Kafka consumer group: масштабирование партициями и consumer'ами; лимиты — в API Gateway для синхронного контура                                                               |
| **Транзакционная целостность распределённых шагов** | Saga ( choreography через события; компенсирующие транзакции в доменах) вместо XA/транзакций Camel                                                                            |
| **Мониторинг и SLA маршрутов**                      | Observability-стек: lag consumer group, deadlock-детекты, SLA на end-to-end задержку; вместо метрик Camel-маршрутов                                                           |

## 7. Поэтапный план вывода ESB (strangler fig)

Вывод ESB — поэтапный (см. MoSCoW: «big-bang»-переключение всех интеграций одним релизом —
Won't have на этот год; полный поэтапный вывод шины за год остаётся в объёме):

1. **Инвентаризация (Q1):** каталог всех маршрутов Camel с классификацией
   (транспорт / потоковое преобразование / batch-преобразование / ФЛК / бизнес-логика /
   только проксирование) и владельцем-доменом. Выгрузка правил ФЛК в репозиторий контрактов.
2. **Подготовка целевых механизмов (Q1–Q2):** Kafka + Schema Registry + CDC-коннекторы в
   лендинг-зонах, API Gateway с IAM, стандартные retry/DLQ/retry-topic-конвенции платформы.
3. **Параллельный прогон (Q2–Q3):** новые механизмы работают **параллельно с Camel**
   (dual-run): событие пишется и в шину, и в Kafka; сверка результатов — критерий включения.
4. **Перенос групп интеграций (Q2–Q4):** миграция по классам, от простого к сложному:
   1. чистое проксирование → API Gateway;
   2. потоковые трансформации → каноничные схемы + Kafka Streams/CDC;
   3. batch-каналы → batch-коннекторы платформы;
   4. маршруты с ФЛК → контракты + валидаторы;
   5. оркестрации с бизнес-логикой → доменные сервисы (Saga/Outbox) — последними,
      вместе с возвратом бизнес-логики из DWH (P2).
5. **Вывод (Q4):** остановка Camel-маршрутов после подтверждения параллельного прогона;
   ESB остаётся в режиме «только чтение» для артефактов, затем выводится из эксплуатации.

## 8. Критерии готовности (чек-лист вывода ESB)

- [ ] Каждый маршрут Camel инвентаризирован и имеет: класс функциональности, домена-владельца,
      целевой механизм (Kafka / API Gateway / доменный сервис / batch-коннектор).
- [ ] Все правила ФЛК выгружены в контракты данных; quarantine/DLQ-процесс описан и протестирован.
- [ ] Для каждой мигрируемой интеграции проведён параллельный прогон (dual-run) со сверкой
      результатов — минимум один полный бизнес-цикл (например, месяц отчётного периода).
- [ ] Все потоковые публикации соответствуют каноничным схемам в Schema Registry.
- [ ] Паттерны надёжности воспроизведены: retry/DLQ/идемпотентность/outbox проверены
      нагрузочным тестом и отказом узла (chaos-сценарий).
- [ ] Метрики интеграций переехали в Observability (lag, ошибки ФЛК, SLA end-to-end).
- [ ] Ни один маршрут с бизнес-логикой не выключен, пока логика не запущена в домене
      и не сверена с легаси-поведением.
