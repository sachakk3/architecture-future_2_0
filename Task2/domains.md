## 1. Разделение на домены

Разделение выполнено по трём критериям одновременно:

1. **Организационная структура** (конвейер «двух пицц»/Team Topologies): домен = подразделение, которое владеет своими данными и отвечает за их качество — Головной офис, Клиники, ИИ-компания, Финтех-компания (банк), будущие партнёрские направления.
2. **Bounded Context (DDD)**: у каждого направления свой язык и жизненный цикл данных — «пациент» в клинике ≠ «клиент» в банке ≠ «подписчик» в фарме. Общие сущности (клиент/пациент, счёт, услуга) не разделяются физически, а связываются контрактами data-продуктов с обязательным обезличиванием идентификаторов.
3. **Регуляторные контуры**: банковская тайна и медицинская тайна требуют изолированных контуров безопасности (P8 из [Task1](../Task1/problems.md)); поэтому финтех- и медицинский домены имеют собственные IAM-политики, шифрование и аудит.

### 1.1 Реестр доменов

| Домен                                                     | Владелец              | Ключевые данные (владение)                                                       | Data-продукты (публикуются в витрину)                                                                         | Границы (что НЕ входит)                                                                      |
| --------------------------------------------------------- | --------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **D-MED — Медицинский (клиники)**                         | Дирекция клиник       | ЭМК, истории болезни, результаты исследований, расписание, инвентаризация клиник | `patients_ops` (обезличенные операционные срезы), `medical_events` (операционные события), `clinic_inventory` | Аналитика мед. карт и историй болезни — **сознательно не создаётся**; ИИ-модели — домен D-AI |
| **D-AI — ИИ-сервисы**                                     | ИИ-компания           | Обучающие выборки, версии моделей, метрики качества                              | `ai_quality_metrics`, `model_predictions` (обезличенные)                                                      | Мед. карты в «сыром» виде — получает только обезличенные выборки из D-MED                    |
| **D-FIN — Финтех (банк)**                                 | Банк                  | Счета, платежи, кредитный портфель, фин. история, скоринговые модели             | `accounts_transactions`, `credit_portfolio`, `fintech_events`                                                 | Медицинские данные; скоринг лечится от зависимости от DWH                                    |
| **D-CORP — Корпоративный (головной офис)**                | Головной офис         | Финансовая отчётность, HR/персонал, инвентаризация, консолидированные KPI        | `consolidated_kpi`, `finance_reporting`, `hr_analytics`                                                       | Операционные данные клиник/банка — только агрегаты по контрактам                             |
| **D-PART — Партнёрские направления (фарма, электроника)** | Новые бизнесы         | Каталоги продукции, договоры поставки, заявки, телеметрия оборудования           | `pharma_catalog`, `device_telemetry`                                                                          | Доступ к ПДн пациентов запрещён — только агрегированные спросовые срезы                      |
| **D-PLAT — Платформенный (Data Platform Team)**           | Платформенная команда | Kafka, CDC, витрина данных, каталог, semantic layer, IAM/Governance              | Сам является поставщиком платформенных сервисов, не данных о бизнесе                                          | Не содержит бизнес-логики доменов                                                            |
| **D-LEG — Легаси-DWH**                                    | Временный владелец    | Исторические данные всех направлений                                             | Только экспорт через CDC (заморожен на запись)                                                                | Не принимает новую бизнес-логику (правило закреплено архитектурным советом)                  |

## 2. Потоки данных между доменами (логика DFD)

Типы потоков (все — через платформенный слой, напрямую домены не связаны):

| Тип потока         | Механизм                     | Правило                                                                     |
| ------------------ | ---------------------------- | --------------------------------------------------------------------------- |
| **Событийный**     | Kafka (event backbone)       | Домен публикует события; подписчики — другие домены и их data-платформы     |
| **Пакетный/CDC**   | Debezium, batch-коннекторы   | Историческая миграция из D-LEG в доменные платформы (B6)                    |
| **Контрактный**    | Data-продукты + Data Catalog | Доступ по контракту через витрину данных, с обезличиванием и проверкой прав |
| **API-синхронный** | API Gateway                  | Операционные запросы в реальном времени (скоринг, оплата)                   |

### Как сценарии обеспечены потоками

- **B3 (ИИ-анализ мед. данных):** `D1 ЭМК → обезличивание → D3 выборки для обучения → AI-инференс → результаты исследования → обратно в ЭМК`. Поток **замкнут внутри медицинского контура** (D-MED ↔ D-AI); в витрину данных попадают только метрики качества моделей — мед. карты, истории болезни и результаты исследований в аналитике не используются.
- **B4 (новый финтех-сервис):** событие «услуга оказана» из D-MED через Kafka → финтех-сервис оплаты/кредита; скоринг обращается **только к данным своего домена** (банковское ядро, кредитный портфель). Новый финтех-сервис не требует изменения DWH и ESB.
- **B1/B2 (отчётность):** все доменные платформы публикуют data-продукты → витрина данных (каталог + semantic layer + конструктор) → отчёт доменного пользователя или консолидированный KPI головного офиса.
- **B5 (партнёры):** фарма/электроника подключаются через (а) онбординг нового домена из шаблона платформы и (б) контракты на обезличенные data-продукты (спросовые срезы, телеметрия оборудования). Точки интеграции — Kafka и витрина данных, DWH не затрагивается.
- **B6 (миграция легаси):** DWH → CDC → доменные платформы; после миграции срезов DWH переводится в read-only и выводится.

## 3. Аргументация разделения: преимущества для бизнеса

| Преимущество                             | За счёт чего достигается                                                                                                                                                 | Какой сценарий ускоряет                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| **Ускорение вывода продуктов**           | Новый сервис (например, «кредит на лечение») живёт внутри финтех-домена и использует его данные; не нужно согласовывать изменения в общем DWH и ждать релизного окна     | B4: новый финтех-сервис запускается за недели вместо месяцев          |
| **Снижение зависимости от DWH**          | Бизнес-логика возвращается в домены; DWH замораживается на запись и мигрирует через CDC; после миграции — вывод из эксплуатации                                          | B6 + P1/P2/P9 из Task1: очередь трансформаций исчезает                |
| **Независимое развитие направлений**     | Каждый домен выбирает свой стек (Python/Go/Java), релизный цикл и команду данных; точки соприкосновения — только стабильные контракты (Kafka-топики, API, data-продукты) | B3: ИИ-компания обучает и выкатывает модели, не согласовывая с банком |
| **Масштабирование на новые бизнесы**     | Онбординг нового домена = развёртывание типовой платформы из шаблона + публикация data-продуктов; централизованных доработок нет                                         | B5: фарма и электроника подключаются за дни                           |
| **Комплаенс и безопасность**             | Мед. и банковские данные изолированы в своих контурах; кросс-доменный доступ — только обезличенные срезы по контракту, с аудитом                                         | Регуляторные требования банка и медицины выполняются конструктивно    |
| **Единая консолидация без дублирования** | Единые метрики в Semantic Layer; KPI собираются из сертифицированных data-продуктов, а не из «кастомизаций поверх BI»                                                    | B2: доверие к цифрам, отчётность за часы                              |

## 4. Что сознательно НЕ разделяется

- **Идентификация клиента/пациента** — единый мастер-идентификатор (Master Data) остаётся платформенным сервисом D-PLAT: без него кросс-доменные срезы (сколько клиентов банка являются пациентами клиник) невозможны. Личными данными Master Data не владеет — только псевдонимизированные ключи.
- **Единые бизнес-метрики** — Semantic Layer в D-PLAT гарантирует «одну цифру» во всех доменах (B2).
