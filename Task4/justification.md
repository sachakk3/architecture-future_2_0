# Обоснование конфигурации Terraform — «Будущее 2.0»

**Связанные документы:** [`diagram.png`](diagram.png) (диаграмма автоматизации) · [`apply-result.png`](apply-result.png) (результат apply) · [`README.md`](README.md)

## 1. Выбор провайдера и облака

Инфраструктура разворачивается в **Yandex Cloud** (провайдер `yandex-cloud/yandex`, ставится с зеркала `terraform-mirror.yandexcloud.net`):

- это облако выбрано компанией для миграции ландшафта (см. Задание 1): данные медицинских и финансовых контуров должны находиться в РФ и соответствовать требованиям регуляторов (152-ФЗ, требования ЦБ, медицинская тайна);
- провайдер поддерживает все необходимые IaaS-примитивы: VPC, подсети, ВМ, диски, NAT-шлюзы, security groups;
- аутентификация — через IAM-токен в переменной окружения `YC_TOKEN` либо через `credentials.auto.tfvars` (исключён из git). Токены и ключи не попадают в репозиторий.

## 2. Состав ресурсов и параметры

### Сеть (`yandex_vpc_network`, `yandex_vpc_subnet`)

- Единая VPC-сеть `future20-network` — изолированный контур проекта.
- **Три подсети**: публичная `10.10.0.0/24` (зона A) под bastion и две сервисные `10.10.2.0/24` (зона A) и `10.10.1.0/24` (зона B). Сегментация закладывает границу между управляющим контуром (bastion) и сервисным (app); CIDR `/24` оставляет запас адресов для масштабирования.
- Подсеть зоны B создана и готова: в учебной песочнице зона `ru-central1-b` для ВМ недоступна, но в продакшне сервисные ВМ распределяются по двум зонам — примитив отказоустойчивости, заложенный в код.

### Виртуальные машины (`yandex_compute_instance`)

- **Bastion (2 vCPU / 4 GB / 10 GB, core_fraction 20%)** — единственная точка входа SSH (jump-host). Нагрузка минимальна, поэтому 2 vCPU/4 GB достаточно; `core_fraction 20%` — гарантированный уровень производительности vCPU для служебных ВМ без переплаты за полные ядра.
- **Сервисные ВМ app-1/app-2 (2 vCPU / 4 GB, core_fraction 20%)** — под целевые сервисы «Будущего 2.0». Обе размещены в зоне A (ограничение песочницы); в проде — по одной в каждой зоне. `core_fraction 20%` на платформе standard-v1 — единственный доступный в песочнице уровень вместе с 5% и 100%; для 2 vCPU это даёт предсказуемую производительность.
- **Preemptible = false** для всех ВМ: сервисы не прерываются ради экономии.
- **`allow_stopping_for_update = true`** для сервисных ВМ — изменение ресурсов (vCPU/RAM) через Terraform требует остановки инстанса; флаг делает изменение управляемым и воспроизводимым, а не ручным.
- SSH-ключи передаются через `metadata` — секреты читаются из локального файла инженера и не хранятся в коде.

### Диски

Фактические квоты учебной песочницы жёстко ограничены (~10 GB SSD и ~10 GB HDD на папку, ~16 GB памяти на зону), поэтому проверяемая конфигурация использует: bastion — 10 GB HDD, app-1 — 8 GB SSD, app-2 — 8 GB HDD (см. `apply-result.png` — apply завершён успешно при этих размерах).

**Продакшн-вариант** (зафиксирован в `diagram.png` и в значениях по умолчанию `variables.tf`): boot-диски 30 GB `network-ssd` + отдельный диск данных 50 GB `network-ssd` на каждый app-инстанс. Отдельный дисковый ресурс даёт: SSD-производительность для баз/индексов и независимый жизненный цикл — пересоздание ВМ не затрагивает данные. Отдельные диски (`yandex_compute_disk`) в песочнице запрещены — поэтому в проверяемой конфигурации они объединены с boot-дисками.

### NAT Gateway и Security Groups

- **Продуктовый вариант** (диаграмма): NAT Gateway + Route Table `0.0.0.0/0 → gateway` для приватных подсетей; Security Groups — SSH к app-ВМ только от SG bastion, сервисный трафик только внутри приватных подсетей, egress через NAT.
- В песочнице Практикума создание NAT Gateway и правил SG запрещено API (подтверждено ошибками первого apply: `Operation is not permitted in the folder`, `Permission denied to add ingress rule`). Проверяемая конфигурация использует `nat = true` на ВМ; изоляция достигается сегментацией подсетей и bastion-моделью. Возврат к прод-варианту — это добавление уже спроектированных блоков `yandex_vpc_gateway` / `yandex_vpc_security_group` в `main.tf`.

### Labels

Все ресурсы помечены `project=future20`, `environment=prod`, `managed-by=terraform` — основа FinOps-отчётности и автоматического учёта затрат по доменам (важно для целевой архитектуры из Заданий 1–3).

## 3. Почему декларативный подход (IaC), а не ручное развёртывание

1. **Декларативность**: конфигурация описывает желаемое состояние («какая сеть и сколько ВМ должно существовать»), Terraform сам вычисляет порядок создания и зависимости (сеть → подсети → ВМ). Ручное развёртывание неизбежно порождает ошибки последовательности и расхождения со схемой.
2. **Воспроизводимость**: `terraform apply` из репозитория даёт идентичную инфраструктуру в любой папке/окружении. Мы проверили это практически: при смене учебного аккаунта инфраструктура была воспроизведена в новой папке тем же кодом за минуты.
3. **Управляемый дрейф**: state-файл — инвентаризация инфраструктуры; `plan` показывает расхождение фактического состояния с кодом до любых изменений. В этой работе план/apply честно зафиксировали как успешные создания, так и управляемое пересоздание bastion при смене размера диска.
4. **Ревью и аудит**: изменения инфраструктуры идут через pull request с diff — видно, кто и зачем изменил подсеть или размер ВМ (требование ИБ для мед./фин. контуров).
5. **Масштабируемость**: `app_vm_count`, объектные переменные (`bastion_vm`, `app_vm`) и CIDR-переменные позволяют менять парк правкой одной строки. Новый домен = тот же шаблон с другим `network_name` — прямой вклад в сценарий «онбординг новых бизнесов за дни» из роадмапа (Задание 3).

## 4. Соответствие бизнес-сценариям

| Ресурс/решение                                             | Сценарий                                       |
| ---------------------------------------------------------- | ---------------------------------------------- |
| Подсеть зоны B в коде + план распределения app-ВМ по зонам | Отказоустойчивость мед./фин. сервисов (B3, B4) |
| Bastion-модель SSH-доступа                                 | Контроль административного доступа (комплаенс) |
| Сегментация подсетей (публичная/сервисные)                 | Изоляция контуров; переход к NAT+SG в проде    |
| Параметризация (`app_vm_count`, CIDR, размеры ВМ)          | Масштабирование на новые бизнесы (B5)          |
| Labels + Terraform-managed ресурсы                         | FinOps и учёт затрат по доменам                |
| IaC-подход целиком                                         | Воспроизводимость сред, ревью изменений        |
