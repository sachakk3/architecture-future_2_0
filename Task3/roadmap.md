# Роадмап трансформации «Будущее 2.0» (горизонт: 12 месяцев)

**Связанные документы:** [tech-radar.md](tech-radar.md) · [`practicum-techradar/`](practicum-techradar/) (интерактивный радар) · [../Task2/domains.md](../Task2/domains.md) (домены) · [../Task1/prioritization.md](../Task1/prioritization.md)

Сценарии: **B1** — быстрая отчётность; **B2** — кросс-доменные KPI; **B3** — ИИ-анализ мед. данных; **B4** — новый финтех-сервис; **B5** — подключение партнёров (фарма/электроника); **B6** — вывод легаси-DWH.

## Обзор этапов

```
Мес 1-2        Мес 3-5            Мес 6-8              Мес 9-12
[Этап 0]  →   [Этап 1]      →    [Этап 2]        →    [Этап 3]
Фундамент     Платформа +         Витрина данных +      Онбординг партнёров,
ИБ/комплаенс  миграция DWH        перенос логики        вывод легаси, DR
```

---

## Этап 0. Фундамент: облако, ИБ, комплаенс (месяцы 1–2)

**Цель бизнеса:** безопасный плацдарм в облаке; снятие регуляторных рисков до начала миграции данных.

| Что делаем                                                                                        |
| ------------------------------------------------------------------------------------------------- |
| Развёртывание облачных лендинг-зон (изолированный аккаунт/проект на домен), Terraform/IaC         |
| IAM/SSO (Keycloak + AD), RBAC/ABAC-модель доступа, Vault для секретов                             |
| Data Governance-контур: классификация данных, правила маскирования ПДн, аудит                     |
| Контуры DR: геораспределённое развёртывание, политика бэкапов для критичных систем клиник и банка |
| Архитектурный совет: правила «новая логика не попадает в DWH», стандарт контрактов данных         |

| Ожидаемый результат                                                                                                    | Ответственные                                   | Ресурсы                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Лендинг-зоны и IAM в проде; политика безопасности согласована с ИБ и регуляторным контуром; шаблон нового домена в IaC | Платформенная команда + ИБ + облачный провайдер | 4–6 инженеров платформы, 2 ИБ-специалиста, бюджет облака ~15% целевого, консультант по комплаенсу |

**Обоснование:** без ИБ-контура миграция мед./фин. данных в облако недопустима (P8, P6 из Task1) — этап убирает главный блокер и снижает риск санкций регулятора. Эффект: качество сервиса (безопасность), возможность масштабирования.

## Этап 1. Интеграционный слой и начало миграции DWH (месяцы 3–5)

**Цель бизнеса:** развязать домены, начать уход от легаси без остановки бизнеса.

| Что делаем                                                                                             |
| ------------------------------------------------------------------------------------------------------ |
| Kafka (event backbone) в проде; первые доменные топики: «услуга оказана» (D-MED), фин. события (D-FIN) |
| CDC (Debezium): поток изменений из легаси-DWH и банковского ядра                                       |
| Доменные Lakehouse: первые два (Медицина, Финтех); первые data-продукты                                |
| Миграция исторических срезов из DWH по приоритету (финансы → медицина → остальное)                     |
| Pilot Data Contracts: контракты для первых data-продуктов                                              |

| Ожидаемый результат                                                                                | Ответственные                                         | Ресурсы                                                                                      |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Kafka и CDC в проде; 2 доменные платформы; ≥6 data-продуктов; ESB обслуживает только легаси-потоки | Доменные команды D-MED, D-FIN + платформенная команда | 3–4 инженера данных на домен, 2 платформенных инженера (Kafka/CDC), лицензии Lakehouse-стека |

**Обоснование:** событийная интеграция снимает зависимость B4 от ESB и DWH — новый финтех-сервис подключается к топику за дни. CDC даёт миграцию «без стоп-крана»: бизнес работает, история переезжает (B6). Эффект: скорость вывода продуктов, снижение риска простоя (единая точка отказа смягчается параллельным контуром).

---

## Этап 2. Витрина данных MVP → промышленная, перенос логики из DWH (месяцы 6–8)

**Цель бизнеса:** запуск портала самообслуживания — главный продукт спринта; остановка роста логики в DWH.

| Что делаем                                                                                                        |
| ----------------------------------------------------------------------------------------------------------------- |
| Витрина данных MVP: портал + Data Catalog + Semantic Layer + Report Builder, интеграция с IAM                     |
| Миграция топ-20 BI-отчётов в витрину данных; сертификация метрик в Semantic Layer                                 |
| Перенос доменной бизнес-логики из DWH в сервисы доменов (скоринг — в финтех-домен, обезличивание — в мед. контур) |
| Корпоративная Lakehouse + консолидированные KPI для головного офиса                                               |
| Data Quality-проверки на входе в data-продукты                                                                    |

| Ожидаемый результат                                                                                          | Ответственные                                                                         | Ресурсы                                                                                              |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Портал в проде; ≥200 активных пользователей; отчёт строится ≤5 минут (против часов); DWH заморожен на запись | Платформенная команда (портал) + все доменные команды + BI-команда (миграция отчётов) | 3 разработчика портала (TS/React), 2 инженера semantic layer, 1 инженер на домен для миграции витрин |

**Обоснование:** прямое закрытие P1/P9 (часы→минуты) — ускоряет принятие управленческих решений (B1, B2); заморозка DWH останавливает рост долга (P2). Замена BI-кастомизаций едиными метриками устраняет расхождения цифр — качество решений. Эффект: скорость решений, снижение затрат на поддержку BI-зоопарка.

## Этап 3. Партнёры, вывод легаси, DR (месяцы 9–12)

**Цель бизнеса:** масштабирование экосистемы (фарма, электроника) и завершение ухода от легаси.

| Что делаем                                                                                    |
| --------------------------------------------------------------------------------------------- |
| Онбординг фарма- и электронного доменов из типового шаблона платформы (IaC)                   |
| Контрактная публикация обезличенных спросовых срезов для фармы; приём телеметрии оборудования |
| Завершение миграции срезов из DWH; DWH → read-only → вывод из эксплуатации                    |
| Замена PowerBuilder современным интерфейсом МИС/ЭМК; демонтаж ESB                             |
| DR-учения по всем критичным контурам; FinOps-оптимизация облачных затрат                      |

| Ожидаемый результат                                                           | Ответственные                                                                   | Ресурсы                                                                                              |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 2 новых домена в проде; DWH выведен; ESB выведен; DR-планы проверены учениями | Доменные команды D-PART + платформенная команда + домены D-MED/D-FIN (демонтаж) | 2–3 инженера на новый домен (в основном шаблон + настройка), 1 команда на миграцию интерфейса клиник |

**Обоснование:** онбординг из шаблона доказывает масштабируемость модели (B5) — следующий бизнес подключается за недели; вывод DWH/ESB/PowerBuilder снижает затраты на поддержку устаревшего оборудования и лицензий (P5) и закрывает риски неподдерживаемого стека. Эффект: масштабирование, снижение TCO, качество сервиса (DR-учения).
